# REVIEW.md — nostr-station Phase 1 discovery

Read-only senior-engineering review of the current `main` (`claude/review-nostr-station-SelxP`,
parent `1a89404`). No code changes. Findings are line-referenced; severity and
prioritisation deferred to `PLAN.md`.

> **Scope note.** The original brief described an Ink "five-phase onboard
> pipeline" with verbs `onboard / doctor / tui / update / uninstall / push /
> setup-editor / relay (subcommand)`. Those were removed in a documented
> simplification cut (see comment at `.github/workflows/ci.yml:59-61`). This
> review targets the current surface — a single Node process that boots a
> browser dashboard plus an in-process Nostr relay — per the user's Phase-1
> direction. The brief's nine themes are preserved; section content is mapped
> onto the real surfaces.

The codebase: 81 TS/TSX files, ~26 kLOC of source, 50 test files (~3 s suite),
two CI workflows (build/smoke + weekly Linux e2e). Node ≥22, ESM, TS strict.

## 1. Architecture map

### 1.1 Process model

One foreground Node process per running station:

```
nostr-station (bare)  →  src/cli.tsx:67  →  Chat.tsx
                                              ├── startWebServer(:3000)     src/lib/web-server.ts
                                              │     ├── maybeStartInprocRelay()    src/lib/web-server.ts:657
                                              │     │     └── Relay(:7777)         src/relay/index.ts
                                              │     ├── maybeStartWatchdog()       src/lib/web-server.ts:704
                                              │     └── maybeStartAutoSync()       src/lib/web-server.ts (~695)
                                              └── tryOpenBrowser()           src/commands/Chat.tsx:30
```

PID file at `~/.nostr-station/pid` (`src/lib/pid-file.ts`); `stop`/`down`
SIGTERMs it (`src/cli.tsx:70-95`).

### 1.2 Module layering

| Layer | Files | Concern |
|---|---|---|
| CLI entry | `src/cli.tsx` (310) | argv dispatch, `--json` short-circuit, `requireInteractive` guards |
| CLI views | `src/commands/*.tsx` (10 files) | Ink renders, command-specific state |
| CLI UI primitives | `src/cli-ui/{Select,Prompt,Step,palette}.tsx` | Reusable Ink widgets |
| Dashboard server | `src/lib/web-server.ts` (2120) | HTTP server, auth middleware, route dispatch |
| Route handlers | `src/lib/routes/*.ts` (12 files, ~6 kLOC) | Per-feature HTTP endpoints |
| Domain logic | `src/lib/*.ts` (~40 files) | Projects, sync, AI, auth-bunker, nvpn, installers |
| In-process relay | `src/relay/*.ts` (5 files) | WS + NIP-01/11/42, SQLite store, whitelist |
| AI tool-loop | `src/lib/ai-tools/*.ts` (8 files) | Provider streaming, tool dispatch, sandbox |
| Static client | `src/web/{index.html,app.js,terminal.js,markdown.js,…}` | Vanilla JS dashboard |

Layering reads cleanly top-down. `routes/*.ts` import from `lib/*` (correct
direction); no `lib/*` imports a `routes/*`. The few violations:

- **`Status.tsx` mixes UI and probing.** `gatherStatus()` and `formatStatusJson()`
  are exported from a React component file (`src/commands/Status.tsx`) and
  also called from `cli.tsx:41` *and* from the dashboard's `/api/status` route.
  Probing is `execSync` with 2 s timeouts (`Status.tsx:115-123`) — a CLI
  component owns business logic that the HTTP server depends on.
- **`maybeStartInprocRelay` hard-binds three subsystems.** Watchdog and
  auto-sync only run if the relay started (`web-server.ts:693-695, 706`); the
  optional-relay envvar (`STATION_INPROC_RELAY=0`) implicitly disables both.

### 1.3 Onboarding flow (replaces the brief's five-phase pipeline)

Onboarding is now three browser screens served from `src/web/index.html` +
state machine in `app.js`:

1. **Welcome** — first paint of `/setup`.
2. **Pair Amber** — full-screen QR over `nostrconnect://` URI generated by
   `startSetupAmber()` (`src/lib/auth-bunker.ts:416-474`). User scans in Amber,
   approves. Bunker pubkey + client secret persisted to
   `~/.nostr-station/bunker-client.json` (mode `0o600`,
   `src/lib/bunker-storage.ts:61`).
3. **Verify** — `runSetupAmberFlow` (`auth-bunker.ts:504-537`) signs a kind-1,
   publishes to the in-process relay, reads it back. User npub written to
   `~/.nostr-station/identity.json` (NEVER an nsec — explicit rejection at
   `src/lib/identity.ts:214`).

No "phases" object, no Ink wizard, no rollback machinery. The Ink CLI has
nothing in this flow. Errors surface as inline status text in the browser.

### 1.4 Command surface (actual)

|---|---|---|---|

**Flag inconsistencies:**

- `--yes` exists on `publish`, `nsite publish/deploy`, `add`, `ai remove` —
  but **not** on `seed`, `keychain delete`, `keychain rotate`, `editor`,
  `nsite init`. These commands have no scriptable, non-interactive escape
  hatch.
- `--json` exists **only** on `status`. `publish`, `seed`, `nsite *`,
  `ai list`, `keychain list`, `add` all lack a machine-readable variant.
- `--raw` is `keychain get` only; the same need ("emit value to stdout for
  shell capture") doesn't apply anywhere else.
- `list` is both a top-level verb (`nostr-station list` ≡ `add` with no arg)
  and a subcommand (`keychain list`, `ai list`). Two meanings, same word.

## 2. Component cohesion audit

The brief's "first-class tool" list was tied to the Ink-wizard architecture.
In the current code, the equivalent question is: do the installable tools
and the embedded relay share a uniform contract across CLI / dashboard /
`status` / `add` / `doctor` (n/a today)?

### 2.1 Per-tool contract gap matrix

| Tool | Detect | Install | Configure | Status surface | Dashboard surface | Logs | Uninstall |
|---|---|---|---|---|---|---|---|
| Relay (in-process) | `gatherStatus` in `Status.tsx` | always started by `maybeStartInprocRelay` | env vars only (`STATION_INPROC_RELAY`, `RELAY_HOST/PORT`) | ✓ `status` row "Relay" | `/api/relay/*` + Relay tab | `log-buffer.ts` ring | n/a (in-proc) |
| `ngit` | `detect.ts:findBin` | `ngit-installer.ts` (pinned tag + SHA256, `sudo -n install`) | none | ✓ row "ngit" | used by `routes/repo.ts`, `routes/ngit.ts` (788 LOC) | subprocess stdout passthrough | undocumented |
| `nak` | `findBin` | `nak-installer.ts` (pinned, SHA256) | none | ✓ row "nak" | used by `seed`, `auth-inproc-relay` | subprocess passthrough | undocumented |
| `nvpn` | `findBin` + `probeNvpnStatus` | `nvpn-installer.ts` (pinned, SHA256, `sudo -n install-cli`) | systemd / launchd service install | ✓ row "nostr-vpn" | `/api/nvpn/*` + `routes/nvpn.ts` (376 LOC) | tail-log via dedicated endpoint | undocumented |
| `claude-code` | `findBin` | not installable here (external) | reads `.claude/` | ✓ row "claude-code" | "Open in AI" handoff | n/a | n/a |
| `stacks` (Soapbox) | `findBin` | via `add stacks` | `Soapbox.config.json` per project | ✓ row "Stacks" | `routes/projects.ts` Stacks deploy panel | subprocess stream | undocumented |
| `nsyte` (`nsite`) | `findBin` | via `add nsyte` | per-project config | not in `status` ✗ | `Nsite.tsx` only (no dashboard panel) | subprocess passthrough | undocumented |
| AI providers | `ai list` reads `~/.nostr-station/ai-config.json` | `ai add <p>` (keychain) | per-provider model/endpoint | not in `status` ✗ | "Open in AI" + Chat (Nori) | none | `ai remove <p>` |
| Bunker / identity | reads `identity.json` + `bunker-client.json` | `runSetupAmberFlow` | rotate via re-pair | not in `status` ✗ | `routes/identity.ts` (656 LOC) | none | manual rm |

**Observations:**

- `status --json` (`Status.tsx:115-180`) is the only "is the world healthy"
  surface and it asks 7 questions: Relay, nostr-vpn, watchdog, ngit,
  claude-code, nak, Stacks. **It does not check `nsyte`, AI providers,
  bunker pairing, or identity.json existence.** A user whose Amber pairing
  broke gets no diagnostic from `status`.
- Installers (`ngit-installer.ts`, `nak-installer.ts`, `nvpn-installer.ts`)
  follow a consistent shape — pinned version (`src/lib/versions.ts`), SHA256
  via `src/lib/checksum.ts` constant-time compare, `/tmp` cleanup on error,
  `sudo -n install` to `/usr/local/bin` — but each is a hand-written script
  rather than an instance of a shared `Installer` interface. The
  duplication is mechanical (~150 lines each).
- "Uninstall" is undocumented and has no command. To fully remove the
  product a user must manually delete: `npm uninstall -g nostr-station`,
  `~/.nostr-station/`, `~/.cargo/bin/nvpn`, `/usr/local/bin/{nak,ngit,git-remote-nostr}`,
  `~/.nvm` (if `install.sh` installed it). None of this is in `README.md`.

### 2.2 Visual / interaction cohesion (CLI)

`src/cli-ui/{Select,Prompt,palette}.tsx` are used consistently across
commands (`Seed`, `Nsite`, `Ai`, `Add`, `Editor`, `Completion`, `Keychain`).
**`src/cli-ui/Step.tsx` has zero importers** (confirmed by grep) — dead code.

Spinners/progress are *not* unified. Each command renders progress its own
way: `Seed` shows `published/total`, `Nsite` streams `nsyte` stdout raw,
`Add` shows last 12 log lines, `Chat` shows a status string. No shared
`Step`/`Spinner` composite (despite `Step.tsx` existing).

Success/error glyphs and color (`palette.ts`) are uniform — single source
of truth, no hardcoded colors anywhere.

## 3. UI / UX consistency

### 3.1 Ink render performance

- **`Status.tsx:115-123` does `execSync` with 2 s timeouts** (`nc`, `nvpn`,
  binary `--version`). The same `gatherStatus()` is called by the dashboard
  HTTP route. On a slow box, `status` can stall 10-20 s and during that
  time `/api/status` blocks the HTTP request loop.
- **`Nsite.tsx:74` calls `dirMtime()` / `lastCommitTime()` during render**
  (not in `useEffect`). These shell out via `execSync`; a hung `git log`
  freezes the UI.
- **`Add.tsx:78`** sets `process.exitCode = 1` inside a `useEffect` with no
  dependency array — fires every render. Harmless (same write each time)
  but a code-smell.

### 3.2 Output mode parity

Only `status` has `--json`. The `status --json` path **bypasses Ink
entirely** (`cli.tsx:40-42`) so nothing pollutes stdout — well-designed
contract. Every mutating command (`publish`, `nsite publish/deploy`, `add`,
`ai add/remove`, `keychain set/delete/rotate`, `seed`) lacks a structured
output mode; the result of a `publish` run is parseable only by colour
inspection of Ink output.

**Mixed stream issue:** `Nsite.tsx:342-367` writes subprocess stdout via
`proc.stdout?.on('data')` into Ink state while Ink also renders to stdout.
Order of frames vs. raw subprocess output is not guaranteed; visible as
interleaved lines under load.

### 3.3 Exit-code patterns (three styles in one CLI)

| Style | Where | Risk |
|---|---|---|
| Explicit `process.exit(n)` | `cli.tsx:42, 80, 84, 89, 92, 121, 200, 217, 228, 235` | Synchronous, deterministic — fine |
| `process.exitCode = n` then let Ink unmount | `Seed.tsx:182`, `Publish.tsx:87-91`, `Nsite.tsx:323-325`, `Editor.tsx:34`, `Add.tsx:78,143`, `Keychain.tsx:78` | Race if Ink hangs on terminal teardown |
| `setTimeout(() => process.exit(...), 100)` | `Ai.tsx:152, 230, 297` | Non-deterministic; exit code depends on phase setter racing with timeout |
| `Status` always exits 0 | `cli.tsx:38-45`, `Status.tsx` | **A failing health probe never produces a non-zero exit**. Scripts that gate on `nostr-station status` cannot detect failure. |

The `Status.tsx:280-282` branch that exits 0 if `json` prop is true is dead
code — `cli.tsx:44` always mounts Status with `json: false` (the `--json`
path is handled in `cli.tsx:40-42` before mount).

### 3.4 Dashboard UX

- `src/web/app.js` escapes via `escapeHtml()` consistently (verified across
  50+ template-literal call sites). Markdown rendered via `marked` →
  `DOMPurify.sanitize` (`src/web/markdown.js:88`). Fallback to `escapeHtml`
  when libs are missing.
- Terminal tabs use `visibility: hidden` rather than `display: none` to
  preserve xterm scrollback — intentional, documented in `terminal.js`.
- Theme state and tab state in `localStorage`; values are typed (theme is
  an enum; Ditto theme JSON validated by `markdown.js` PURIFY_CONFIG).
- Static asset cache headers: `no-cache` on `src/web/*` files
  (`web-server.ts:214`), `public, max-age=604800, immutable` on
  `/vendor/xterm/*` (`web-server.ts:151`) with cache-busting query strings
  in `index.html`.

## 4. Code health

### 4.1 TypeScript strictness

`tsconfig.json` has `strict: true` and `skipLibCheck: true`. Notably
**absent** (defaults — off):

- `noUncheckedIndexedAccess` — array/object bracket access typed as
  non-undefined. Hot path: `cli.tsx:27` (`args.indexOf(f); return args[i+1]`).
- `exactOptionalPropertyTypes` — `foo?: string` accepts `undefined` as a
  value.
- `noImplicitOverride`
- `noFallthroughCasesInSwitch` — relevant for `cli.tsx`'s 18-case switch.

### 4.2 `any` / unsafe casts

| Pattern | Count | Notes |
|---|---|---|
| `: any` annotations | 274 | Concentrated in `web-server.ts` (29), `nvpn.ts` (27), `routes/ngit.ts` (22), `routes/repo.ts` (21), `routes/projects.ts` (21), `auth-bunker.ts` (19), `routes/identity.ts` (18) |
| `as any` casts | 23 | `relay/index.ts` (8), `routes/ai.ts` (5), `ai-tools/tool-loop.ts` (3) |
| `@ts-ignore` / `@ts-expect-error` | 2 | Rare — good |

Most `any` is on Node HTTP request/response bodies and parsed JSON. There
is **zero use of `zod` or `valibot`** anywhere in the tree (`grep` for both
returned 0). Input validation is hand-rolled: typically `JSON.parse` in a
try-catch, then string-coercion and whitelist checks (see
`routes/projects.ts:674` and `routes/ai.ts:311` for the pattern).

The pattern is safe in practice — values get coerced via `String()` or
checked against an enum before use — but the absence of a schema layer
means each route invents its own validation and there's no single audit
point for "what does the API accept".

### 4.3 Error handling

- **No process-level `unhandledRejection` / `uncaughtException` handler**
  (grep returned only a comment in `Chat.tsx:24`). An unawaited rejection
  in a route handler will surface as Node's default warning to stderr.
- React commands lean on `useEffect` async IIFEs; several lack outer
  try/catch:
  - `Publish.tsx:30-72` (loading phase)
  - `Ai.tsx:57-72` (`AiList`)
  These would propagate to Ink's error boundary and produce an opaque red
  banner.
- HTTP routes consistently use `try { ... } catch (e) { res.writeHead(500); ... }`
  — the dashboard side is well-defended.

### 4.4 Logging

`src/lib/log-buffer.ts` (68 lines) is a ring-buffer for service logs (used
by the dashboard's log tail endpoint). It is **not** used as a general
logger. Outside of `cli.tsx`'s help text, there are only 8 `console.*`
calls in `src/`:

- `routes/patches.ts` (2), `routes/identity.ts` (2), `routes/status.ts` (1),
  `routes/issues.ts` (1), `auto-sync.ts` (1), `commands/Status.tsx` (1).

No leveled logging (debug/info/warn/error), no structured logs, no
environment-controlled verbosity. The dashboard's log surface is
service-tail rather than application-log.

### 4.5 Async / process patterns

- `execSync` / `execFileSync`: 37 call sites. Biggest concentrations:
  `git-identity.ts` (12), `projects.ts` (4), `routes/projects.ts` (3),
  `Status.tsx` (3). Inside HTTP handlers, `execSync` blocks the event loop.
- `AbortController` usage: 6 sites only. Long-running ops (the AI tool-loop
  exec, the projects sync, the dashboard SSE streams) do not consistently
  thread a signal through. The AI tool-loop `Tool result` audit
  (cross-check) noted that an exec started under an HTTP request continues
  running until its own timeout when the client disconnects.
- No `shell: true` anywhere (`grep` returned 0). All `spawn`/`execa` calls
  use argv arrays — command-injection-resistant by construction.

### 4.6 Dead code & duplication

- `src/cli-ui/Step.tsx` — zero importers.
- `src/lib/web-server.ts:266-363` — `loadProviderConfig()` v0.x fallback
  reads `~/.claude_env` on every request, no cache, even though the new
  provider config (`ai-config.json` + keychain) is what every fresh install
  uses.
- Three installer files (`ngit-installer.ts`, `nak-installer.ts`,
  `nvpn-installer.ts`) share ~80 % of their code (resolve target, download,
  SHA256 verify, extract, `sudo install`, cleanup on error). No shared
  helper.
- `routes/projects.ts` (1144 LOC) is one function — `handleProjects` —
  dispatching across ~20 subroutes. Sub-modules (`projects-git`,
  `projects-sync`, `projects-chat`, `projects-stacks`) would fall out
  cleanly without behavioural change.

## 5. Security & privacy

### 5.1 nsec never on disk — verified

- `src/lib/identity.ts:214` explicitly rejects any string starting with
  `nsec` before persisting to `identity.json`.
- `src/lib/projects.ts:282` repeats the rejection at the project-API
  boundary.
- Grep across `auth*.ts`, `identity.ts`, `bunker-storage.ts` for write
  paths found: `clientSecretHex` (the NIP-46 ephemeral client key, *not*
  the user's identity nsec) in `bunker-storage.ts:61`, and
  `watchdog-nsec` / `seed-nsec` (app-owned helper keys) in the keychain.
  No user-nsec write path exists.

### 5.2 Bunker client key at rest

`~/.nostr-station/bunker-client.json` written with `chmod 0o600`
(`bunker-storage.ts:61, 65`). Plaintext JSON — documented threat-model
trade-off in the file header comment (lines 11-17): "the worst an attacker
with FS access can do is cause Amber prompts on the user's phone, not sign
arbitrary events." That stance is consistent with `SECURITY.md`.

### 5.3 Keychain abstraction

`src/lib/keychain.ts` ships three backends with platform-aware selection
(`keychain.ts:193-203`):

- macOS → `security` CLI (`MacOSKeychain`, lines 32-71)
- Linux + GNOME → `secret-tool` / libsecret (`LinuxKeyring`, 76-102)
- Headless / no libsecret → AES-256-GCM encrypted file at
  `~/.config/nostr-station/secrets`, key derived via scrypt over
  `machine-id + homedir` (`EncryptedFileBackend`, 108-178).

Backend name is exposed via `getKeychainBackendName()` (line 210) — the
user *should* see which backend is active. Verify in the dashboard UI.

**Gap:** rotate (`Keychain.tsx:193-272`) writes the new value, keeps the
old as a session-rollback in `oldValueRef`, then "forgets" it. On the
encrypted-file backend, the old plaintext fragment may remain in the JSON
store until the next write. No secure-erase (`sodium_memzero`-equivalent).
Realistic but worth flagging.

### 5.4 NIP-42 + relay write gating

- Challenge: `crypto.randomBytes(32)` per WebSocket connection
  (`src/relay/index.ts:192`). Validated against kind-22242 with ±10 min
  `created_at` window (`index.ts:236-254`). Per-connection scope is
  adequate replay protection for a local relay; not a global nonce.
- **Default write state on fresh install: closed.** `getOwnerHex()` returns
  null when no `identity.json` exists; the gate at `index.ts:302-318`
  rejects any non-whitelisted, non-owner write. Onboarding writes the
  user's npub to `identity.json`, making the user the implicit owner.
- Whitelist persists to `~/.nostr-station/data/whitelist.json` atomically
  via temp+rename (`whitelist-store.ts:82-87`).

### 5.5 Relay DoS / validation gaps

`src/relay/index.ts`:

- **No max event size enforced.** Default WS frame size is large.
- **No per-connection subscription cap.** NIP-11 advertises max 100 globally
  (line 158), but the code does not enforce a per-connection limit.
- **No idle / slowloris timeout** on connections.
- **No future-timestamp ceiling on `created_at`.** Events dated a year
  ahead are accepted. The ±10-min window applies only to NIP-42 AUTH
  events.
- **Tag shape unchecked.** `Array.isArray(e.tags)` is verified (line 392)
  but inner shape (each tag must be `string[]`) is not.

Defaults are loopback-bound (`index.ts:73`, dashboard at
`web-server.ts:2086`), so exposure is local-only — but a malicious local
process can still misbehave.

### 5.6 Dashboard auth / origin

- Bind: `127.0.0.1` only (`web-server.ts:2086`, env override
  `DEV_HOST`).
- DNS-rebinding guard: Host header validated against an allowlist
  (`127.0.0.1 / localhost / [::1] / ::1`) at `web-server.ts:800, 829-840`.
- CSRF guard: POST/PATCH/PUT/DELETE require Origin or Referer matching
  loopback (`web-server.ts:810, 842-862`).
- Token-in-query fallback for `EventSource` / WS / `<a download>` carries a
  64-hex bearer in `?token=` (`864-879`); Origin/Referer re-checked on
  upgrade.
- Session auth via NIP-98 with localhost-exempt during setup
  (`web-server.ts:843, 1068`).

Defences are layered and consistent across endpoints. The terminal
WebSocket (`routes/terminal.ts:127-207`) replays Host + Origin checks at
upgrade time and caps frames at 64 KiB.

### 5.7 AI tool-loop sandbox

The full picture is in the Section-4 file `src/lib/ai-tools/`. Highlights:

- All exec via `spawn(argv[0], argv.slice(1), …)` — array argv, no shell
  (`exec.ts:122-125`).
- Per-call denylist (`exec.ts:36-50`) blocks the obvious footguns:
  `rm -rf /`, `rm -rf ~`, `git push --force`, `git reset --hard`,
  `npm publish/unpublish`, `curl`, `wget`, `sudo`, fork-bombs.
- `path-safety.ts` (47-132) layers: NUL byte reject, absolute path reject,
  `..` traversal reject, `realpathSync` symlink canonicalisation against
  the project root.
- Approval gate (`approval-gate.ts` + `tool-loop.ts:503-522`) consulted for
  every gated tool; `build_project` previews resolve to the actual npm
  script being executed (lines 116-129), so an injected
  `"build": "rm -rf ~"` is visible before user approval.
- API keys read from keychain only; stored in `ai-config.json` as
  `keyRef: "keychain:ai:<id>"` pointers (`ai-config.ts:9, 48`). Never
  logged.

**Gap 1.** `write_file` approval preview truncates content to 400 chars
(`tool-loop.ts:96-102`). A 4 MB benign-looking prefix could hide a payload
beyond it. Practical risk is low (user signed off on path + byte count)
but worth noting.

**Gap 2.** Exec timeout is local to the child (`exec.ts:138-141`). If the
HTTP client disconnects mid-tool, the child runs to its own timer. Low
risk in practice; worth tying to the request lifecycle.

**Gap 3.** Tool results go back to the model as raw text (JSON-encoded);
file contents read by `read_file` and `git_diff` can carry prompt-injection
strings. No explicit delimiters around untrusted blocks in the system
prompt. The trust boundary depends on model-side mitigation.

### 5.8 Network integrity

All three installers download from pinned `github.com` release URLs,
verify against a pinned SHA256 (`src/lib/versions.ts` + `checksum.ts`),
extract to `/tmp`, then `sudo -n install`. No GPG sig. On mismatch, the
tmp dir is removed (`nvpn-installer.ts:131`, equivalent in the others).

`install.sh` itself is fetched over HTTPS with no signature. The contract
is "trust github.com TLS" — same as Homebrew, rustup, nvm.

## 7. Distribution & install

### 7.1 `install.sh` contract

70 lines. `set -euo pipefail`. Steps: OS guard → optional nvm/Node 22 →
PATH augment → `npm install -g nostr-station@latest --silent` → `exec
nostr-station`. Idempotent for Node (skip if already ≥22). Idempotent for
the npm install (re-fetches latest each run; will rebuild optionalDeps).

**Hijack surface:** the canonical `curl … | bash` has no `sha256` /
signature check. Same posture as Homebrew/nvm/rustup. Matches stated
design.

**Junk on failure:** nvm install writes to `~/.bashrc` / `~/.zshrc`
silently (`install.sh:50`). If the script fails *after* nvm wrote rc
hooks, the user is left with nvm in their shell rc and no nostr-station.
No rollback.

### 7.2 npm package hygiene

`package.json` `files`: `["dist", "install.sh", "README.md"]`. Tarball is
~1.5 MB. No `node_modules`, no `src/`, no secrets. `bin: { "nostr-station":
"dist/cli.js" }`. `engines.node: ">=22"`. `optionalDependencies: node-pty`.
No `postinstall` script.

**Pre-release tag:** `package.json:3` is `"version": "0.0.6-0"` — npm
pre-release per semver. `CHANGELOG.md` top entry is `[Unreleased]`. Verify
this is intentional (not a leftover from a partial publish).

### 7.3 node-pty graceful absence

`src/lib/terminal.ts:115-135` dynamic-imports `node-pty`; on failure
returns `null` and callers degrade — the terminal panel becomes
unavailable but the dashboard keeps serving. The optional dep is the right
mechanism; absence is handled.

### 7.4 No `uninstall` verb

The brief lists `uninstall` as a command; it was removed. Today removing
the product requires manual cleanup of `~/.nostr-station`, `~/.cargo/bin/nvpn`,
`/usr/local/bin/{nak,ngit,git-remote-nostr}`, and optionally `~/.nvm`. This
is undocumented in `README.md` and `CONTRIBUTING.md`.

## 10. Cross-cutting summary

The product is in better shape than the brief implied. The simplification
cut (Ink wizard → browser dashboard + in-process relay) eliminated a large
amount of moving infrastructure (Docker, Rust, launchd / systemd
authoring, multi-phase rollback). What remains is one Node process with a
focused set of CLI verbs and a substantial browser dashboard. Tests are
solid, security model is consistent and well-documented in `SECURITY.md`,
and the dashboard's defence-in-depth (loopback bind + Host/Origin/CSRF +
NIP-98 + path safety) is layered correctly.

The highest-leverage cleanup opportunities, in rough order:

1. **Stale references to removed verbs** in `package.json:18` and
   `.github/workflows/e2e-linux.yml`. The e2e workflow may be silently
   exercising nothing useful.
2. **`status` always exits 0** — scripts can't detect failures.
3. **CLI exit-code style is three patterns deep** — settle on one.
4. **No process-level unhandled-rejection / uncaught-exception handler.**
5. **No schema validation library** anywhere — 274 `: any` annotations,
   hand-rolled JSON validation per route.
6. **`Status.tsx` runs `execSync` probes** that block the dashboard's
   `/api/status` HTTP loop.
7. **Three near-identical installers** (`ngit`, `nak`, `nvpn`) without a
   shared `Installer` helper.
8. **`routes/projects.ts` (1144 LOC, one function)** is the standout
   refactor target.
9. **Relay validation gaps:** future-timestamp ceiling, max event size,
   per-connection subscription cap, idle timeout.
10. **No macOS CI** for `install.sh` or onboarding.
11. **`Step.tsx`, `loadProviderConfig` legacy fallback** — dead/legacy code.
12. **`completion` missing from `README.md`**, `keychain rotate --rollback`
    missing from CLI help text.

These translate into a P0/P1/P2/P3 plan in `PLAN.md` (next phase).
